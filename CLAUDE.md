# Oxychloride

Rust re-implementation of Eclipse OCL over Ecore models, plus Henshin graph transformations (textual syntax and `.henshin` models, equivalent), QVT model transformations (Operational Mappings `.qvto` and Relations `.qvtr`, as Eclipse QVTo/QVTd) and code generation (Python, Rust) from metamodels with their OCL: library, `oxy` CLI, JSON-RPC/C ABI integration API, VS Code extension (with graphical metamodel and rule diagram editors). See README.md, docs/ARCHITECTURE.md, docs/CODEGEN.md, docs/HENSHIN.md, docs/QVT.md and docs/PROJECTS.md.

## Commands
- `cargo test` — all engine/CLI/FFI/LSP tests. The `oxy-codegen` tests generate code into `target/codegen-tests` and run it with `python3` and `cargo` (offline); they skip themselves when those are missing.
- `cargo clippy --all-targets` must be warning-free; `cargo fmt` (rustfmt.toml: max_width 120).
- VS Code extension (`vscode/`, client of `oxy lsp`): `cargo build -p oxy-cli`, then `cd vscode && npm run build`; `npm test` runs its integration tests in a real VS Code. `npm run typecheck` also checks the webview pages (`webview/`: the transformation view, the metamodel diagram and the rule diagram, React Flow + ELK, bundled for the browser). Both diagrams can be driven headlessly with `.claude/skills/run-oxychloride/driver.mjs` (the real page and engine, a stand-in host).
- Manual check: `cargo run -p oxy-cli -- run examples/library/library.ocl -m examples/library/library.xmi` (expects 3 violations, exit code 1).
- Manual check (textual): `cargo run -p oxy-cli -- run examples/university/university.oclinecore examples/university/university.hutn` (expects 5 violations: 3 invariants, 2 postconditions; exit code 1).
- Manual check (projects): `cargo run -p oxy-cli -- check --project examples/shop` (8 documents checked, no problems); `oxy new /tmp/shop` creates the same project (11 files).
- Manual check (QVT): `cargo run -p oxy-cli -- qvt examples/qvt/uml2rdbms.qvtr -e examples/qvt/uml.oclinecore -e examples/qvt/rdbms.oclinecore --in source=examples/qvt/company.hutn --hutn` (prints the schema: 8 relations applied, 13 objects created; `uml2rdbms.qvto` prints the same schema).

## Conventions
- Layering: `oxy-ecore` ← (`oxy-ocl`, `oxy-henshin`) ← `oxychloride` ← (`oxy-lsp`, `oxy-cli`, `oxy-ffi`); `oxy-cli` runs `oxy-lsp` as `oxy lsp`. `oxy-henshin` does not depend on `oxy-ocl`; the workspace checks transformation states against OCL. `oxy-codegen` and `oxy-qvt` depend on `oxy-ecore` and `oxy-ocl` only, and are used by `oxychloride`. Front ends talk to the engine only through `oxychloride` (preferably `rpc::Server`, so all transports stay identical).
- Never panic on user input: loaders return `LoadError`/warnings, OCL problems are `Diagnostic`s, evaluation failures are `Value::Invalid` with a reason.
- Name resolution logic exists twice (checker in `check.rs`, evaluator in `eval.rs`) and must stay in sync: variables → the host's names (QVT: `this`, model parameters, properties) → implicit iterator/`self` properties → types; calls without a source try the implicit sources' operations (metamodel, `def:`, the host's contextual ones), then the host's global ones, then the library. The checker records what it resolved (`resolution.rs`, `Environment::analysis`); code generation reads that instead of resolving again, so new resolutions in the checker must be recorded there too.
- Code generation (`crates/oxy-codegen`, docs/CODEGEN.md): targets only read the `CodeModel` (`model.rs`) and `library.rs`, never the metamodel; runtimes are files under `crates/oxy-codegen/runtime/<language>/` copied into the output; generated code never depends on the engine. Untranslatable OCL is a warning plus code that fails at run time, never a generation error. Adding a language: follow "Adding a target language" in docs/CODEGEN.md (register it in `TARGETS`; front ends discover it through `codeTargets`). Engine changes to OCL semantics need a check in `crates/oxy-codegen/tests/conformance.rs`.
- QVT (docs/QVT.md, `crates/oxy-qvt`): QVT is built on `oxy-ocl`, not beside it — Imperative OCL and QVTo's expressions are `ExprKind`s parsed by the OCL parser's QVT dialect (`syntax/parser/imperative.rs`; the QVTo/QVTr document parsers drive the public `Parser`), checked and evaluated by the OCL checker and evaluator; what depends on the transformation goes through the `CheckHost`/`Host` traits (`host.rs`), which the compilers and runs of `oxy-qvt` implement. Model types/imports are `PackageAlias`es; they are resolved through a lookup the workspace gives (nsURI, package registry, file next to the document). Runs work on a copy of the workspace's models (`runQvt` never changes the workspace). Unsupported constructs are diagnostics, never panics; recursion is bounded by depth limits (the evaluator grows its stack). QVTo units (`import a.b.c;` → `a/b/c.qvto` next to the importing file or above) are parsed at their own span offsets (`Parser::with_offset`), so every span tells its unit; their code runs with their own model types (`Evaluator::set_aliases`). `examples/qvt/uml2rdbms.qvto` (which imports `sql/Types.qvto`) and `.qvtr` must produce the same schema (tested).
- Henshin (docs/HENSHIN.md): a `.henshin` model is read into the syntax tree of the textual syntax (`oxy_henshin::xmi::read`) and compiled by the one compiler; `xmi::write` writes the *compiled* module, keeping a template's ids. Never give the two syntaxes separate semantics. Changes of the syntax or the compiler need the round trip to stay a fixpoint (`crates/oxy-henshin/src/xmi/tests.rs`, `henshin_models_mean_what_their_texts_mean`); the example `.henshin` files must stay in sync with their texts (regenerate with `oxy convert`). Rule diagram ids are names (`r`, `r/m`, `r#g`, `<scope>::n`, `<scope>::s->t:ref`, `u@1`), computed by `diagram/henshin.rs`'s `Index` for drawing and editing alike.
- Protocol changes: update `protocol.rs`/`rpc.rs`, `docs/PROTOCOL.md` and `vscode/src/engine.ts` together.
- Metamodel and rule diagrams (`crates/oxychloride/src/diagram/`, `vscode/src/diagram.ts`/`ruleDiagram.ts`, `vscode/webview/diagram/`/`rules/`): the text is the only source of truth — diagram edits are `editMetamodel` requests that return minimal text edits (OCLinEcore on the syntax tree, `.ecore` on the XML), applied to the shared TextDocument; positions live in `<file>.diagram.json`. Element ids are names (`pkg::Class.feature`), computed identically from the metamodel and the syntax; tests in `crates/oxychloride/tests/diagram.rs`.
- Tests use `examples/library` and `examples/university` (and `examples/philosophers` for state spaces; `examples/shop` is the project `oxy new` creates, kept equal to the templates by a test: regenerate it with `oxy new … --force` after changing them); when adding engine features, add cases to `crates/oxy-ocl/tests/library.rs` (OCLinEcore/HUTN workspace behaviour: `crates/oxychloride/tests/textual.rs`; the package registry: `crates/oxychloride/tests/registry.rs`; Henshin transformations and the two syntaxes: `crates/oxychloride/tests/transform.rs`; rule diagrams: `crates/oxychloride/tests/rule_diagram.rs`; reading/writing `.henshin`: `crates/oxy-henshin/src/xmi/tests.rs`; QVT languages: `crates/oxy-qvt/tests/{operational,relational}.rs`, QVTo imports and libraries: `crates/oxy-qvt/tests/imports.rs`; QVT documents and runs in the workspace: `crates/oxychloride/tests/qvt.rs`; projects: `crates/oxychloride/tests/project.rs`, `oxy new`/`oxy check` of a project: `crates/oxy-cli/tests/project.rs`).
- Modeling projects (docs/PROJECTS.md, `crates/oxychloride/src/project.rs`, VS Code `vscode/src/projects.ts`): a folder with `oxychloride.json` (folders, registry, codegen); new projects and documents come from the engine's templates (`newProject`, `newDocument`; `oxy new`), which must stay free of errors (tested in `crates/oxychloride/tests/project.rs`, which opens each part alone and all of them, in both metamodel formats). The extension reads manifests itself: keep `ProjectManifest`/`ProjectFolders` defaults, `vscode/schemas/oxychloride.schema.json` and `projects.ts` in sync. A project's registry is part of the extension's package registry; registering a file of a project writes its manifest.
- Package registry (`crates/oxychloride/src/registry.rs`, VS Code `vscode/src/registry.ts`, setting `oxychloride.registry`): URIs (nsURIs or placeholders) → metamodel files, loaded first on `reload`. Every `.ecore` load in the workspace goes through its `Locator` (never `Metamodel::load_ecore_file` directly), and every lookup of a metamodel by URI (imports, `xsi:schemaLocation`) asks it too.
- Documents have a language (`.ocl`, `.oclinecore`, `.hutn`, `.xmi`, `.henshin_text`, `.henshin`, `.qvto`, `.qvtr`). OCLinEcore documents rebuild `mm` from `base_mm`, model documents (HUTN, XMI) rebuild `model` from `xmi_model` (see docs/ARCHITECTURE.md); public operations mark what changed (`mm_dirty`, `xmi_stale`, `models_dirty`) and end with `Workspace::finish`, which rebuilds the derived state once.
